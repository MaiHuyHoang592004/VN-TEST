# ADR-07: Database invariants live in hand-written migration SQL, not the Prisma schema

## Status

Accepted (M1 core foundation).

## Context

Prisma's schema language has no `CHECK` construct. The alternative the M1 plan
originally proposed — generate the init migration, then hand-edit
`migration.sql` to insert the constraints — makes the most load-bearing file
in the schema the one file with no source of truth in `schema/`: every future
`prisma migrate dev` regenerates its own `migration.sql` from the Prisma
schema and has no way to know the hand-added `ALTER TABLE ... ADD CONSTRAINT`
statements should be preserved. A regenerated init migration would silently
drop every invariant below.

## Decision

CHECK constraints are appended, as plain SQL, to the end of
`prisma/migrations/20260912000000_v2_init/migration.sql` — generated by
`prisma migrate dev --create-only`, then extended by hand once, not
re-generated. Because Prisma has no model for `CHECK`, `prisma migrate diff`
never sees these statements as schema it should reproduce, so there's no
drift in either direction: the constraints aren't something Prisma will ever
try to "fix" by dropping.

Each constraint, verbatim, with its rationale:

```sql
ALTER TABLE "InventoryBalance"
  ADD CONSTRAINT balance_nonneg CHECK ("onHand" >= 0 AND "reserved" >= 0),
  ADD CONSTRAINT balance_reserved_within_onhand CHECK ("reserved" <= "onHand");
```
A balance can never go negative, and reserved stock can never exceed on-hand
stock — the two numbers this table exists to keep truthful.

```sql
ALTER TABLE "InventoryReservation"
  ADD CONSTRAINT reservation_qty CHECK ("quantity" > 0 AND "consumedQuantity" >= 0 AND "consumedQuantity" <= "quantity");
```
A reservation for zero or negative quantity is meaningless; consumption can
never overshoot what was reserved.

```sql
ALTER TABLE "InventoryMovement"
  ADD CONSTRAINT movement_not_noop CHECK ("onHandDelta" <> 0 OR "reservedDelta" <> 0);
```
`InventoryMovement` is the append-only ledger — a row that changes nothing is
a bug in the caller, not a valid event.

```sql
ALTER TABLE "OrderItem"       ADD CONSTRAINT order_item_qty CHECK ("quantity" > 0);
ALTER TABLE "FulfillmentItem" ADD CONSTRAINT fulfillment_item_qty
  CHECK ("quantity" > 0 AND "producedQuantity" >= 0 AND "producedQuantity" <= "quantity");
ALTER TABLE "ShipmentItem"    ADD CONSTRAINT shipment_item_qty CHECK ("quantity" > 0);
ALTER TABLE "ShopifyFulfillmentOrderLine" ADD CONSTRAINT sfol_remaining_nonneg CHECK ("remainingQuantity" >= 0);
```
Line-item quantities are always positive; produced/remaining quantities can
never exceed or go below the ordered quantity — the same
not-more-than-was-asked-for invariant as the reservation check above,
repeated at every stage goods move through (order → fulfillment → shipment →
channel sync).

```sql
ALTER TABLE "BomComponent"
  ADD CONSTRAINT bom_component_qty CHECK ("quantityPerUnit" > 0 AND "wastageRate" >= 0 AND "wastageRate" < 1);
```
A BOM line consuming zero material isn't a component; wastage is a fraction
of input, so it must be `[0, 1)` — `1` would mean the process consumes
material and produces nothing, which isn't representable.

```sql
ALTER TABLE "PriceListItem"
  ADD CONSTRAINT price_item CHECK ("minQuantity" >= 1 AND "unitPrice" >= 0);
```
A price break below quantity 1 is meaningless; a negative unit price is
always a data-entry bug, never a real price.

```sql
ALTER TABLE "ExceptionCase"
  ADD CONSTRAINT exception_has_subject
  CHECK (num_nonnulls("ingestionRecordId", "orderId", "fulfillmentId", "shipmentId") >= 1 OR "subjectKey" LIKE 'store:%');
```
Every exception must point at something concrete to resolve — one of the four
subject FKs, or a `store:<id>` subject key for the one case (a store-level
problem, e.g. token expiry) that has no row of its own to reference.

```sql
ALTER TABLE "OutboxEvent" ADD CONSTRAINT outbox_attempts_nonneg CHECK ("attempts" >= 0);
ALTER TABLE "IngestionRecord" ADD CONSTRAINT ingestion_attempts_nonneg CHECK ("attempts" >= 0);
```
Attempt counters are monotonically-increasing counts; negative is always a
bug in the worker loop that decremented instead of incremented.

## Consequences

- A schema-only reviewer of `prisma/schema/models/*.prisma` will not see these
  rules — they must know to also read `migration.sql` (or this ADR). This is
  the cost accepted in exchange for the migration history staying the single
  source of truth for the database's actual shape.
- `npm run db:diff` (`prisma migrate diff --from-migrations ... --to-schema ...
  --exit-code`) reports zero drift from these constraints in either direction,
  by construction — Prisma's diff algorithm is schema-driven and never
  introspects `CHECK` constraints it didn't create.
- Adding a new invariant later means: write the `ALTER TABLE ... ADD
  CONSTRAINT` as a new, separate migration (never edit `20260912000000_v2_init`
  after it has shipped), and add an entry to this file.

## Known limitation (unrelated to CHECK constraints)

`npm run db:diff` currently reports one false-positive on the partial index
`fulfillment_active_queue` (`Fulfillment.status, dueAt`, `WHERE status IN
(...)`) — "removed index" + "added index" on the same columns, even though the
generated `CREATE INDEX ... WHERE (...)` in `migration.sql` matches the
`@@index(..., where: raw(...))` in `fulfillment.prisma` exactly. This is the
known Prisma partial-index diff bug referenced in the M1 plan (Task 2 Step 7);
it persists at Prisma 7.8.0, the latest stable 7.x at time of writing. Do not
"fix" it by removing the partial index — `npm run db:diff`'s exit code should
be read as "review the output," not "must be 0," until Prisma resolves this
upstream.
