move it to finished/ and update the ledger below in the same commit.

what remains needs hardware, credentials or a real day's traffic rather than
code. When that happens its open items DO NOT travel to finished/ with it —
they move to §3c below, in this file, which stays in the active folder. A
pending item filed under finished/ is a pending item nobody reads again.

3b. PARKED — DECIDED TO DEFER, NOT FORGOTTEN
--------------------------------------------------------------------------------
Things a phase deliberately left undone that belong to NO single doc, so they
would otherwise live only in a commit message nobody re-reads. Each says what
it is, why it was skipped, and what should trigger picking it up.

P1. LIVE NOTIFICATION DELIVERY.  ✅ DONE 2026-07-22 by doc 05, exactly as this
    entry prescribed: the bell polls the existing query every 60s while the tab
    is visible, pauses when it is hidden, and refreshes the moment it comes
    back. No SSE, no realtime vendor. Raise the cost before raising the
    frequency if a bench ever wants faster. Original entry, for the record:
    Raised by doc 04, 2026-07-22.
    The panel is real and audience-routed — the right people get the right
    events — but it only refreshes when the page does. A notification raised
    while someone sits on a screen does not appear until they navigate.
    Why deferred: the events landed first because routing is the part that is
    expensive to get wrong; delivery is a transport swap on top of a panel that
    already works, and it costs nothing to add later.
    PICK IT UP WHEN: doc 05's fulfillment stations start. A packer standing at
    a bench needs work to appear without navigating, which is the first time
    this stops being a nicety. Cheapest first move is polling the existing
    unread-count query on an interval; SSE only if that proves too slow or too
    chatty. Do NOT reach for a websocket service — Vercel Functions support SSE
    on the default runtime, and a third-party realtime provider would be a new
    vendor for a problem an interval solves.

P2. NOTIFICATION PREFERENCES / DIGESTS.  Raised by doc 04, 2026-07-22.
    Every event notifies every member of its audience, immediately. Nobody can
    mute a category, and a busy warehouse rota will feel that first.
    Why deferred: entirely speculative until real volume exists — the current
    restraints (one line per assignment batch, silence on routine internal
    steps, nobody notified of their own action) may well be enough.
    PICK IT UP WHEN: someone actually complains, or a rota exceeds a few dozen
    notifications a day. Not before; a preferences table nobody uses is worse
    than no preferences.

P3. SEARCH IS DEMO DATA AIMED AT ROUTES THAT DO NOT EXIST.  Raised by the
    mobile nav pass, 2026-07-22.
    Two independent breaks, either one fatal. /api/search still reads
    src/lib/search-data.ts — the demo dataset CLAUDE.md says to swap for Prisma
    "when the database lands", which it did three docs ago. And resultHref in
    search.tsx sends every hit to /orders/<id> or /products/<id>, NEITHER of
    which is a route: every successful search ends on the coming-soon page. The
    feature reads as finished from the outside, which is why it survived this
    long.
    Done now, not deferred: the mobile search row and its dock tab are gone. A
    tab costing a fifth of a phone's navigation has to work. The sidebar keeps
    its box, so the entry point survives for when the index is real.
    PICK IT UP WHEN: order or catalogue volume makes scrolling a table
    unreasonable — the first moment search earns its keep. Two pieces, in
    order: point the index at Prisma through libs/db, keeping the /api/search
    contract; then give resultHref somewhere real. /orders already filters on
    ?q= via useTableParams, so an order can land there and no /orders/<id> page
    need ever exist — /catalog wants the same treatment. Restore the dock tab
    only after both, and only if the bar still has room.

4. STANDING DECISIONS THAT APPLY TO EVERY REMAINING PHASE
--------------------------------------------------------------------------------
  • One Next.js app, no separate backend. Logic in transport-agnostic
    services (explicit actor); Server Actions + /api/v1 routes are thin
    adapters. The endpoint ships WITH the feature (doc 03 §8A).
  • Deny by default: every action starts with a guard; every list query
    starts from scopes.ts. A findMany without a scope spread is a defect.
  • Money: Decimal end to end, $transaction + ledger row + audit row
    together, idempotency keys, reason required. Proven by tests in CI.
  • Stay deployable off Vercel (R1-R7 in doc 03): no edge runtime, no
    @vercel/* in business logic, platform services behind interfaces.
  • shadcn on Base UI (render=, never asChild), semantic tokens, Geist spec
    in DESIGN-VERCEL.md, every string through t() in all 7 locales.
  • Prisma: migrations only, never db push / migrate reset.
  • FK when a row makes a claim on something LIVE; a plain id when it states
    something that already HAPPENED. Append-only history (the inventory
    movements ledger, audit logs) keeps reference ids WITHOUT foreign keys, so
    a later edit elsewhere can neither block the past nor cascade it away —
    the BOM line a movement names is replaced wholesale on every BOM save.
    Live claims (a reservation's order) get the constraint, because an orphan
    there holds real stock forever and nothing self-heals it. Decided in full
    in doc 06 §A3.
  • Join to User only where a screen NAMES the person. Otherwise the actor id
    stays a plain column: AuditLog is already the who-did-what trail, and a
    speculative relation costs an edit to the most-referenced model in the
    schema for a join nobody performs. Adding one later is pure metadata.
  • Hono + zod-openapi when the endpoint count passes ~20 — not before.
  • A notification's AUDIENCE is derived from ROLE_PERMISSIONS, never from a
    hard-coded role list — the same table the guards read. Reach and access
    then cannot drift apart, and a role granted a capability starts receiving
    the alerts that capability implies without anyone editing the sender.
