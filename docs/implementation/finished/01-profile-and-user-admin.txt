--------------------------------------------------------------------------------
SECTION 0b — FINDINGS TO RESOLVE BEFORE BUILDING
--------------------------------------------------------------------------------

F1. ROLE COVERAGE. Legacy had 7 roles: admin, customer, warehouse,
    warehouse_admin, warehouse_external, supporter, designer. New enum has 4.
    Missing capability, not just missing names:
      - warehouse_admin = manages a warehouse's staff/stock, not just orders.
      - designer        = sees orders, edits artwork, no money/product access.
      - warehouse_external = a partner who may only see CERTAIN PRODUCTS
                             (legacy did this with configs.products, an
                             untyped JSON allowlist).
    Decision: add WAREHOUSE_ADMIN and DESIGNER to UserRole. Do NOT add
    warehouse_external as a role — it is a *scope*, not a job title. Model it
    as an explicit allow-list relation (see UserAllowedProduct in Phase 1).

F2. ADMIN "ADD USER" CANNOT SET A PASSWORD ANYMORE. Legacy's modal had a
    password field. With Google OAuth + OTP as the primary path, an admin
    typing someone's password is both bad security and usually wrong (the
    user will sign in with Google and never use it). Replace "create user
    with password" with an INVITE flow (UserInvite model, Phase 1).

F3. SESSION STRATEGY MISMATCH. libs/auth sets session.strategy = "jwt", but
    apps/dashboard/src/app/(protected)/layout.tsx has a comment claiming a
    "DB-session check runs server-side per request". With the JWT strategy
    auth() reads and verifies the cookie; it does not hit the database, and
    the Session table is unused. Two consequences:
      (a) The layout comment is wrong and should be corrected.
      (b) You CANNOT revoke a session ("sign out everywhere", "deactivate a
          user and kick them out now") — the JWT stays valid until expiry.
    Decision required. Options:
      Option A (recommended): keep JWT, add a `sessionsValidFrom DateTime?`
        column on User. On deactivate / password change / "sign out
        everywhere", set it to now(); the JWT callback compares token.iat
        against it and rejects older tokens. One column, one comparison, no
        per-request DB read on the happy path if you cache it in the token
        refresh window.
      Option B: switch to database sessions. Cleanest revocation, but the
        Credentials provider does not support DB sessions, so email+password
        login would have to go.
    This doc assumes Option A.

F4. STATUS CHECK IS MISSING AT LOGIN FOR INACTIVE USERS. libs/auth rejects
    BANNED in the Credentials provider only. A user with status INACTIVE can
    still sign in, and Google sign-in checks neither. Fix in the signIn
    callback so it covers every provider (Phase 2, step 2.1).

F5. LEGACY BUGS NOT TO COPY. From the audit of the old system:
      - "Member Since" rendered new Date() instead of created_at.
      - Phone was editable in the form but silently dropped on save.
      - GET /api/user returned the entire user row (balance, debt, tier,
        configs, api key) to the browser on every page load.
      - API key could not be rotated or revoked.
      - Order assignment charged the seller's balance inside an unawaited
        forEach and could double-charge already-assigned orders.
    Each has an explicit countermeasure below.

Rule: one migration per logical change, named. NEVER `prisma db push` or

STATUS 2026-07-20: all 8 migrations applied to LOCAL and PROD. Both databases
report zero drift (`prisma migrate diff` returns an empty migration). Branch
`profile`.

  Deviations from the plan as written, and why:

  D1. `prisma migrate dev` cannot run in this sandbox. Once it has a warning to
      show (e.g. adding a UNIQUE constraint) it demands an interactive
      confirmation, and it checks for a TTY — piping "y" does not satisfy it.
      Migrations 3-8 were therefore authored as SQL and applied with
      `prisma migrate deploy`, which is non-interactive. Still Prisma Migrate,
      still versioned migration files, no `db push` anywhere.

  D2. Migration 3 (warehouse `code`) was hand-written rather than generated.
      Prisma's output was a single `ADD COLUMN "code" TEXT NOT NULL`, which
      succeeds on an empty local DB and FAILS on any populated one. Replaced
      with add-nullable → backfill → set-not-null. Verified by seeding rows
      with duplicate names and a punctuation-only name before applying:
      produced HOCHIMIN-1, HOCHIMIN-2, WH-3. Test rows removed afterwards.

  D3. The legacy cutover script needed four fixes it did not have (see the
      cutover section below). Not optional: two of them would have broken the
      cutover outright or silently mis-assigned staff permissions.

1.0  LEGACY CUTOVER — fixes and the rehearsal harness
--------------------------------------------------------------------------------
`prisma/scripts/migrate-legacy.sql` predates these migrations. Fixed:

  • warehouses INSERT omitted `code`, now UNIQUE NOT NULL — the statement
    would have aborted the whole (single-transaction) cutover.
  • the role CASE mapped only admin/seller/warehouse/support and sent every
    other legacy role to SELLER. Supporters, warehouse managers and designers
    would have arrived with a seller's access and none of their own — silent,
    and a permissions problem in both directions. All 7 legacy roles now map
    explicitly; warehouse_external → WAREHOUSE + allow-list rows.
  • warehouse_members would have been empty: the migration's backfill runs
    before legacy users exist. The same backfill now repeats in the cutover.
  • configs.products (legacy product allow-list) survived only as opaque JSON;
    it now also populates user_allowed_products, skipping ids no longer in the
    catalog rather than failing on the FK.

1.4  WAREHOUSE MEMBERSHIP — the fix for the legacy design
--------------------------------------------------------------------------------
NEW FILE: libs/db/prisma/schema/models/warehouse-member.prisma

Legacy modelled "a warehouse" as a *user account*, so orders pointed at a
person and only one person could hold a warehouse's queue. Our schema already
does the right thing (Order -> Warehouse, User.warehouseId -> Warehouse), but
User.warehouseId is a single FK, which still means one warehouse per person.
A join table removes that ceiling and lets a manager cover two sites.

  /// Which warehouses a staff user works in. Many-to-many so one person can
  /// cover several sites and a site can have many staff.
  model WarehouseMember {
    id          Int       @id @default(autoincrement())
    userId      String    @map("user_id")
    warehouseId Int       @map("warehouse_id")
    /// True for the user's default site — drives the landing view.
    isPrimary   Boolean   @default(false) @map("is_primary")
    createdAt   DateTime  @default(now()) @map("created_at")

    user      User      @relation(fields: [userId], references: [id], onDelete: Cascade)
    warehouse Warehouse @relation(fields: [warehouseId], references: [id])

    @@unique([userId, warehouseId])
    @@index([warehouseId])
    @@map("warehouse_members")
  }

KEEP User.warehouseId for now — it is the user's primary site and existing
code/migrations read it. Rule: WarehouseMember is the source of truth for
"can this user see this warehouse"; User.warehouseId is a denormalised
pointer to the primary membership, written in the same transaction.
// ponytail: two sources of truth is a known smell. Ceiling: they can drift.
// Upgrade path: once every read goes through WarehouseMember, drop the column.

PHASE 2 — BACKEND (libs/auth, libs/db, apps/dashboard server code)
================================================================================
Architecture decision, stated once: THERE IS NO SEPARATE BACKEND. This is
Next.js on Vercel. "Backend" = Server Actions for mutations the dashboard
makes, and Route Handlers (app/api/...) only for things outside the app
(the public seller API authenticated by ApiKey, and webhooks). Do not build a
REST layer for the dashboard to call itself.

2.1  THE PERMISSION LAYER  (build this FIRST — everything depends on it)
--------------------------------------------------------------------------------
NEW: libs/auth/src/permissions.ts

Ask "can this user do X?", never "is this user an admin?". Roles map to
permissions in ONE place, so adding a role later touches one file.

  export const PERMISSIONS = [
    "users.read", "users.create", "users.update", "users.delete",
    "users.roles.manage", "users.balance.manage", "users.impersonate",
    "warehouses.read", "warehouses.manage", "warehouses.members.manage",
    "orders.read.all", "orders.read.own", "orders.read.warehouse",
    "orders.assign", "orders.refund",
    "products.read", "products.manage",
    "transactions.read.all", "transactions.read.own", "transactions.approve",
    "tickets.read.all", "tickets.read.own", "tickets.manage",
    "audit.read",
  ] as const;
  export type Permission = (typeof PERMISSIONS)[number];

  const ROLE_PERMISSIONS: Record<UserRole, Permission[]> = {
    ADMIN:           [...PERMISSIONS],                   // everything
    WAREHOUSE_ADMIN: ["warehouses.read","warehouses.members.manage",
                      "orders.read.warehouse","orders.assign","users.read", ...],
    WAREHOUSE:       ["orders.read.warehouse","warehouses.read", ...],
    SUPPORT:         ["users.read","orders.read.all","tickets.manage", ...],
    DESIGNER:        ["orders.read.all","products.read", ...],
    SELLER:          ["orders.read.own","transactions.read.own",
                      "tickets.read.own","products.read"],
  };

  export function can(user: SessionUser, p: Permission): boolean
  export function permissionsFor(roles: UserRole[]): Set<Permission>

Design rules:
  - Permissions live in CODE, not in the database. A DB-backed permission
    editor is only worth it when non-engineers must change rules at runtime;
    you have 6 roles and one engineer. Revisit if that changes.
  - `.own` / `.warehouse` / `.all` suffixes are how scope is expressed. The
    query layer (2.3) reads these, so scoping is never re-implemented per page.

2.5  SERVER ACTIONS — PROFILE (self-service)
--------------------------------------------------------------------------------
NEW: apps/dashboard/src/app/(protected)/profile/actions.ts

  updateProfile(input)          requireUser. Updates name, phone, locale,
                                timezone, companyName, taxId, avatarUrl.
                                Countermeasure to legacy bug F5b: the action
                                and the form share ONE schema, so a field can
                                never be editable in the UI but dropped on save.
  requestEmailChange(email)     requireUser. Writes pendingEmail, sends an OTP
                                to the NEW address. Never change `email`
                                directly — an unverified swap is an account
                                takeover primitive.
  confirmEmailChange(code)      Verifies, moves pendingEmail -> email, bumps
                                sessionsValidFrom, audits.
  changePassword(current, next) requireUser. Only for users WITH a
                                passwordHash. Verify current, bcrypt the new,
                                bump sessionsValidFrom, audit PASSWORD_CHANGED.
  updateWebhook(url, secret)    requireUser. https-only. Audit WEBHOOK_UPDATED.
  testWebhook()                 Sends a signed ping, returns status + body
                                snippet. (Cheap, and saves hours of support.)
  createApiKey(name)            requireUser. Generate 32 random bytes ->
                                "opc_live_<base62>". Store SHA-256 hash +
                                prefix. RETURN THE RAW KEY EXACTLY ONCE.
                                Audit API_KEY_CREATED.
  revokeApiKey(id)              requireUser + ownership. Sets revokedAt.
  signOutEverywhere()           Bumps sessionsValidFrom.

Every one of these ends with an audit write where the action list in 1.1
names it. Wrap the write + audit in prisma.$transaction so you can never have
a change without its log entry.

2.6  SERVER ACTIONS — ADMIN (user management)
--------------------------------------------------------------------------------
NEW: apps/dashboard/src/app/(protected)/admin/users/actions.ts

  listUsers(query)          requirePermission("users.read") + userScope.
                            Server-side pagination/sort/filter. Returns
                            USER_ADMIN_SELECT only.
  getUser(id)               requirePermission("users.read")
  inviteUser(input)         requirePermission("users.create"). Creates
                            UserInvite + emails the link (reuse the Resend
                            sender in libs/auth). Audit USER_INVITED.
  resendInvite / revokeInvite
  updateUser(id, input)     requirePermission("users.update"). Roles require
                            "users.roles.manage" as a SEPARATE check. Audit
                            with before/after of changed fields only.
  setUserStatus(id, status) requirePermission("users.update"). Deactivating
                            bumps that user's sessionsValidFrom so they are
                            kicked out immediately (this is why F3 matters).
  deleteUser(id)            requirePermission("users.delete"). SOFT delete
                            (deletedAt) — a user with orders/transactions is
                            never hard-deleted.
  topUpBalance(id, input)   requirePermission("users.balance.manage").
                            MUST be one transaction: create Transaction row
                            (TOPUP/COMPLETED) + increment User.balance + audit.
                            Reason is REQUIRED. Idempotency key on the request
                            so a double-click cannot double-credit.
                            (Legacy bug F5e was exactly this, unawaited.)
  refundBalance(id, input)  Same shape, TransactionType.REFUND.
  adjustBalance(id, input)  ADJUSTMENT, admin-only, reason required.

MONEY RULES (non-negotiable):
  - Balance is NEVER written outside a $transaction that also writes the
    Transaction row. If the two can disagree, the ledger is fiction.
  - Amounts are Decimal end to end. No float arithmetic anywhere.
  - Every money action takes a human-entered reason and writes an audit row.

2.8  RATE LIMITING + ABUSE
--------------------------------------------------------------------------------
Minimum viable, do not skip:
  - OTP send + verify: per-email counter (libs/auth already carries a
    ponytail: note that this is missing).
  - changePassword, requestEmailChange, createApiKey: per-user throttle.
  - Public seller API (ApiKey routes): per-key throttle.
Implementation: a small table or Vercel KV counter. Anything is better than
nothing here; the correct sophisticated version can come later.

2.9  TESTS (the check that makes this phase "done")
--------------------------------------------------------------------------------
One test file: apps/dashboard/src/lib/auth/permissions.test.ts (or a plain

  - SELLER cannot list users, cannot read another seller's order, cannot
