0b. THE FOUR QUESTIONS — SETTLED AGAINST THE LEGACY CODE 2026-07-22
--------------------------------------------------------------------------------
All four were answered by reading the archived legacy apps directly
(fulfillment-system-be, fulfillment-fe-new, opcreative-portal). One caveat
applies to every conclusion below: the archive trails legacy PROD by ~10
months, so each is "verify with one query when the DB creds land", not "never
look again". NONE of them block building — the old blocker framing was wrong.

Standing rule for everything in this doc: legacy is a reference for BUSINESS
RULES only. Its implementation is largely what not to do (see O4 and B2's
double-charge). Take the rule, rebuild it on our patterns.

O1. PRICE UNITS — DOLLARS. Divisor stays 1.0.  SETTLED (confirm pre-cutover).
    Five independent signals, no dissent:
      · ProductVariant.price and price_tier_1..4 are `Int` — legacy literally
        cannot express $12.50, so prices were whole dollars only;
      · User.balance and Transaction.amount are `Float`;
      · the charge is a direct `balance - base_cost`, so both share a unit;
      · the UI formats the raw number through Intl USD with NO /100
        (fulfillment-fe-new/src/utils/Number.js);
      · no `* 100` or `/ 100` exists anywhere in the legacy backend.
    Were these cents, a $12.50 item would have displayed as "$1,250" and every
    seller would have noticed. Decimal(12,2) is a strict superset of Int
    dollars — nothing is lost, no conversion needed. Still run the runbook's
    20-row SELECT against real prod before the cutover; leave BOTH
    PRICE_DIVISOR markers in migrate-legacy.sql at 1.0.
    → Does NOT gate the pricing UI. Build A3/A4 now.

O2. PRICING SHAPE — the tier model IS the money model. SETTLED ENOUGH TO BUILD.
    What actually charges a seller is price_tier_{user.tier} on ProductVariant
    (order.service.ts:151) — a 1:1 match for VariantPrice. The four legacy
    fields do exist, but as a `price_config` JSON blob on the PRODUCT
    (price_op_ship, price_customer_ship, shipping_cost_first_item,
    shipping_cost_add_on) that only the NEWER frontend reads; the archived
    backend has no such column and no money path touches them.
    → Build VariantPrice exactly as specced.
    → ONE QUESTION STILL WORTH ASKING THE TEAM: do sellers get quoted a
      different price when they ship themselves? If yes, that is a second
      price DIMENSION — one extra column on VariantPrice plus one line in
      effectivePrice, NOT a redesign. Ask before A4 ships; do not block
      A1/A2/A3 waiting for the answer.
    Also noted: the legacy tier lookup has no fallback, so a seller with a
    null tier got `price_tier_undefined` — a free order. Our effectivePrice
    fallback chain (tier → tier 0 → salePrice) closes that hole; it is a fix,
    not a port.

O3. PER-USER CUSTOM PRICES. Unchanged — deferred, and nothing found in the
    archive argues otherwise. Legacy /users/update-price/:id set bespoke
    prices per seller per variant; tiers 1-4 replace it on the THEORY that
    four bands cover the real spread. Revisit only when a real seller needs a
    price no tier expresses; the change then is a userId column on
    VariantPrice, not a redesign.

O4. WHO CREATES ORDERS — LEGACY ANSWER: EVERYONE, FOR THEMSELVES ONLY.
    This doc previously assumed "admin can create for any seller". That is
    WRONG about legacy. Both create paths hardcode the owner to the caller —
    order.service.ts:50 (form) and :451 (import) each set
    `customer_id = user.id` — and no order form has a customer selector. An
    admin clicking "Add order" therefore created the ADMIN'S OWN order, and
    the admin's balance was charged at assignment. Worth asking the team
    whether that was deliberate or a bug nobody ever hit.
    Legacy's role lists (OrderActionButtons.jsx) only hide BUTTONS; the
    endpoint carried AuthGuard and no role check at all, so any logged-in user
    could post an order. Our server-side gate is a fix, not a port.
    → DECISION: match legacy. createOrder forces customerId = actor.id for
      everyone; skip the admin "create for seller X" feature until support
      actually asks. BUT have the service take an owner parameter rather than
      reading the actor inline — 0c's importers will need it, and it is one
      argument now versus a signature change later.

0c. HOW ORDERS ACTUALLY ARRIVE  (verified in the archive 2026-07-22)
--------------------------------------------------------------------------------
Checked because the whole shape of Phase B depends on it. The app being
replaced has NO ecommerce integration: no Shopify, Etsy, Amazon, eBay,
WooCommerce, Printful or Printify — not a connector, not a webhook receiver,
not an API client. Those words appear in the legacy repo only inside icon
fonts and lockfiles. `Order.marketplace` is FREE TEXT that a human types. The
one webhook module is OUTBOUND (pings the seller's own webhook_url when a
shipment or status changes); nothing flows in.

Orders arrive three ways, all human-initiated — precisely what Phase B builds:
  1. the add-order form   2. the Excel import   3. POST /customer/orders with
  the seller's own API key  →  becomes our B5

TIKTOK SHOP is the only real platform link, and it is half-manual. A separate
TTS microservice (VITE_APP_TTS_API_URL — its own backend, NOT in the archive)
does the OAuth, syncs shops/orders and fetches labels. Getting one INTO
fulfillment is a person clicking Import, hand-mapping every line item to a
product/variant/shape and pasting a mockup link; the browser then LOOPS the
line items calling POST /orders one at a time, then reports Imported /
ImportFailed back to TikTok (TTSOrderPage.jsx:105-175). Close the tab halfway
through a 5-item order and 2 orders exist, 3 are lost, and TikTok is told
nothing. The orders also land on whoever clicked, per O4.

THE WIDER COMPANY — from opcreative-portal's own brief (2026-07-08). Those
repos are NOT in the archive, so this is their documentation, not code we
verified. This app is 1 of ~10 repos. The real marketplace flow for phone
cases is:
    customer orders on a marketplace → a cron on VM 4001 fetches it → merges
    artwork → dispatches over SSH to a Selenium fleet (G1-G5) → auto-fills a
    form on tuoli.icutmax.com → print
which BYPASSES the fulfillment app entirely. Shopify/Stripe/PayPal appear in
that portal for MONEY only (Plaid bank sync + payout matching) — and note OP
Creative OWNS those accounts and rents them to sellers, i.e. one company
account, not multi-tenant OAuth, which matches the one-Stripe-account decision
already in the schema notes. That reconciliation code is uncommitted and never
deployed, and the portal's own orders table is empty in prod.

WHAT THIS CHANGES HERE — three things, none of them a new phase:
  · B5 /api/v1/orders is THE front door for every future integration
    (Shopify, Etsy, TikTok, the VM 4001 cron). Build it complete, not as a
    demo, so that no integration ever needs to reach into the database.
  · B4's importer processes SERVER-side. Legacy looped in the browser and lost
    rows to a closed tab; ours takes the batch and survives it.
  · createOrder takes an owner, defaulted to the actor (O4). Import-on-behalf
    -of is the one genuine "create for someone else" case, and it is coming.

OPEN FOR THE TEAM (doc 06 sized, blocks nothing here): is the VM 4001 →
Selenium → tuoli pipeline still running, and does the new system absorb it or
deliberately stay out of its way?

A4. modules/catalog/product-variants/   (the SKU + pricing core)
    BUILT 2026-07-22. Two things resolved while building, both worth knowing:

    · SKU STATUS NOW EXISTS. ProductVariant had no status column, so this
      spec was unbuildable as written. Added (migration sku_status,
      ProductStatus default ACTIVE) rather than faked with deletedAt, because
      the two mean different things and the grid needs both: status INACTIVE
      retires a SKU that HAS orders behind it (the row must survive them),
      detach is a REAL delete and is refused once any order points at it.
      That split is also what lets the unique constraint below land later
      without a data cleanup — a detached SKU leaves no tombstone to collide
      with when the same variant is attached again.

    · THE ATTACH RACE IS DEFERRED ON PURPOSE, with the answer scheduled.
      Two admins attaching the same variant in the same instant can both pass
      the existence check and create a duplicate row. The real fix is
      @@unique([productId, variantId]) + createMany({ skipDuplicates: true }),
      and it is NOT applied because it hangs on one fact nobody can check
      without legacy prod credentials: whether the old data holds duplicate
      (product, variant) rows. Adding it blind trades a cosmetic duplicate an
      admin can detach for a cutover that aborts on real data. The deciding
      query now sits in migrate-legacy.sql's pre-flight audit with both
      branches written out; run it the day creds land.

    service:  attachVariants(productId, variantIds[]) — creates the missing
              Product×Variant SKU rows, skips existing ones (until the unique
              constraint lands, "existing" = a manual findFirst check).
              updateSku(id, {sku, position, salePrice, status}) ·
              setPrices(productVariantId, prices: {tier, price}[]) — UPSERTS
              the VariantPrice rows in ONE transaction; tier 0 required,
              1-4 optional · bulkSetPrices(ids[], prices) for the
              select-many-fill-once flow the legacy grid had.
    pricing.ts (named file, no utils.ts): effectivePrice(sku, userTier) =
              VariantPrice[tier] ?? VariantPrice[0] ?? salePrice. This is THE
              function Phase B charges money through — it gets its own test
              BEFORE any order code exists (pricing.test.ts: tier hit, tier
              fallback, missing tier 0, Decimal end to end — no floats).
    queries:  by-product SKU list with prices; the seller-facing price a
              catalog page shows is effectivePrice for the VIEWER's tier.

    PAGE /admin/products/[id]/variants:
      Header: product identity + status. "Attach variants" dialog (multi-
      select of Variant rows not yet attached). Grid: variant name, sku,
      position, stock (read-only — inventory is doc 05), tier prices 0-4
      inline-editable, status. Row selection → BulkSetPrices dialog.
      This grid is the reason the shared data-table kit exists; no bespoke
      table code.

A5. modules/catalog/mockups/
    service:  CRUD (name, url, thumbnail, folderId, status). Normalise
              status to "active"/"inactive" strings (schema keeps String —

    PAGE /admin/mockups: table thumbnail/name/url/status + dialogs. Gated

A6. PAGE /catalog  (seller-facing, read-only — products.read)

B2. ASSIGNMENT + MONEY.   BUILT 2026-07-22, orders.money.test.ts green (7
    cases, mutation-verified: deleting the already-assigned guard fails
    exactly the test that names it).
    The part the legacy system got wrong, confirmed at
    order.service.ts:287-292: `orders.forEach(async order => { ... })` reads a
    seller's balance and writes `balance - base_cost` back, unawaited and with
    no transaction. Assign five orders for one seller and all five read the
    SAME starting balance and overwrite each other, so the seller is charged
    for roughly one — money lost silently, no ledger row, nothing to audit.
    Everything below exists to make that failure impossible.
    assignOrders, in ONE $transaction per seller batch:
      1. re-read the orders FOR UPDATE, drop any already-assigned;
      2. charge = Σ effectivePrice(sku, seller.tier) × quantity  (catalog's
         pricing.ts — imported through catalog/index.ts, the domain rule);
      3. decrement seller balance + insert Transaction(ORDER_PAYMENT,
         idempotencyKey) + write baseCost/assignedAt/status on the orders +
         audit row. The unique idempotencyKey makes a retry credit exactly
         once — same pattern the phase-2 money tests already prove.
    orders.money.test.ts (node --test, real DB, same harness as
    money.test.ts): assign twice with one key charges once · balance and
    Transaction always move together · already-assigned orders are skipped
    not re-charged · insufficient balance rejects the whole batch.
    GREEN BEFORE B3 UI EXISTS.

B5. PUBLIC API.   BUILT 2026-07-22. Routes live at app/api/(public)/v1/ —
    NOT in a modules/orders/routes.ts. Next's App Router resolves handlers by
    file path, so that is where they must sit today; the routes.ts convention
    in modules/README.md is the shape they take WHEN Hono lands at ~20

    same mechanism Transaction uses): requiring an Idempotency-Key header
    without a constraint behind it is worse than not requiring one, because it
    promises a guarantee that races. placedAt also became optional-defaulting-
    to-now — legacy overwrote it anyway, and demanding it produced the
    validation message "expected date, received Date", which means nothing to
    the person reading it.
    The first real /api/v1 surface (doc 03 §2.10 already specs
    the wrapper): GET /api/v1/orders (cursor pagination, scoped to the key's
    owner) · POST /api/v1/orders (Idempotency-Key honoured) · GET
    /api/v1/orders/:id. Money as STRINGS, ISO-8601 UTC, the standard error
    envelope. ~5 lines per route over the B1 service — if it is more, the
    service is missing something, fix the service. This is endpoint #1 of
    the "endpoint ships with the feature" rule; Hono lands at ~20, not now.

NOT in Phase B (doc 05): label purchase/print, barcode printing, mockup sync,
the fulfillment scan stations, refund-to-balance on cancellation (needs the
orders.refund flow designed against real usage — the permission is reserved).

C1. modules/finance/transactions/   BUILT 2026-07-22, transactions.test.ts
    green (7 cases). One deviation from the spec below, deliberate:
    approveTransaction takes NO idempotencyKey. The spec assumed one because
    topUpBalance needs one — but that CREATES a row, while approval FINISHES a
    row that already exists, so the guard can be a compare-and-set on the row's
    own status (updateMany WHERE status='PENDING'). That is strictly stronger
    than a client key: it needs nothing from the caller and cannot be defeated
    by sending a fresh one. core/ledger.ts grew settlePendingTransaction beside
    applyBalanceMove, both over one shiftBalance, so the arithmetic and the
    negative-balance rule cannot differ between a top-up and an approved
    top-up.
    Worth recording how that guard was verified: the obvious test — approve
    twice in a row — passes even with the database guard DELETED, because the
    service's status pre-check catches the sequential case. Only a CONCURRENT
    double-approve (Promise.all) actually exercises the compare-and-set. The
    first version of this test had no teeth and looked green.
    queries:  scoped ledger list (transactions scope already in scopes.ts):
              filters user, type, status, date range, search on publicId/
              description. TRANSACTION_ADMIN_SELECT in libs/db selects.ts —
              never the whole row habit stays.
    service:  approveTransaction(actor, id, idempotencyKey) — PENDING TOPUP/
              REFUND only: apply the balance change + set COMPLETED +
              balanceBefore/After + audit, one $transaction, same invariants
              as topUpBalance (reuse that code path — do NOT write a second
              credit routine that can drift from the first).
              rejectTransaction(actor, id, reason) — reason REQUIRED, no
              balance change, audit row.
    guard:    transactions.approve (admin only today).
    test:     approve twice with one key credits once · reject never moves
              balance · approve on a non-PENDING row fails. Extends the
              existing money test file's harness.

C2b. NOTIFICATIONS — added 2026-07-22, before the frontend rather than after.
    The backend had grown three events that changed a seller's money and told
    them nothing: an approved top-up (balance moves in silence), a REJECTED
    top-up (a refusal with the reason stranded in an admin table), and an
    order batch assignment (money leaves without the seller acting — the one
    that most deserves a notice, and the one legacy never sent).
    Added TRANSACTION_APPROVED, TRANSACTION_REJECTED, ORDER_ASSIGNED
    (migration notification_money_events) + all 7 locales. Each notify() sits
    INSIDE the transaction it announces, so a rolled-back credit never sends.
    ORDER_ASSIGNED is one per seller per batch, not one per order — the charge
    is a single move.
    Two things this exercise showed, worth keeping:
      · NOTIFICATION_META is Record<NotificationType, Meta>, so adding an enum
        value FAILS THE BUILD until the panel is wired. Keep that shape; it is
        what stops a backend event existing with no way to render it.
      · Shipping/delivery notifications are NOT here. Shipment rows are not
        created until doc 05, so the event has nothing to fire on yet. The
        panel's "orders" tab and the unused `shipped` locale string are
        waiting for it.
    Note for whoever does the i18n sweep: en/notifications.json still carries
    demo strings from the original design mock (newOrder, lowStock, topup,
    shipped, restock, maintenance) that no NotificationType maps to. `topup`
    in particular duplicates `toppedUp`. Delete the dead ones as part of C3
    rather than translating them into six more languages.
