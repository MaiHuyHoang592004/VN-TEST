LEGACY → NEW STATUS DICTIONARY (memorise this; it resolves every "what maps
to what" question in the build):
  Pending            → PENDING
  Production Ready   → ASSIGNED          (assignOrders already does this)
  In Production      → IN_PRODUCTION     (the SCAN sets it — A4)
  Filled             → not a status: filled >= quantity, derived from the
                       counter (legacy flag dropped on purpose)
  Produced           → dropped (was a manual sub-state; revisit if the floor
                       asks — it is one enum value + one map edit)
  Fulfilled          → FULFILLED         (the PROOF PHOTO sets it — A6)
  Completed          → SHIPPED           (the HANDOFF sets it — A7)
  Pending Dropoff, Design Sorted → already dead in legacy prod; not ported
  Cancel             → CANCELLED
  Wrong Label / Design problems / Out Of Stock / Return
                     → ON_HOLD + note (the note carries which reason)
  Refund             → not a status; money action (orders.refund, reserved)
  tracking_status    → Shipment.trackingStatus (separate carrier axis;
                       raw string, never an enum)

A1. STORAGE — modules/core/storage.ts  (the app's first file upload)
    WHY: proof photos must live somewhere; doc 03 R2/R3 requires platform
    services behind a tiny interface (no @vercel/* in business logic).

    1. `npm i @vercel/blob -w @opcreative/dashboard`.
    2. Create modules/core/storage.ts exporting exactly:
         export type StoredFile = { url: string; pathname: string };
         export async function putObject(input: {
           key: string;            // e.g. "proofs/1Z999AA10123456784-1721650000.png"
           body: ArrayBuffer | Buffer;
           contentType: string;
         }): Promise<StoredFile>;
       Implementation selects by env:
         · BLOB_READ_WRITE_TOKEN set → @vercel/blob `put(key, body,
           {access: "public", contentType})`. Public-unguessable URLs are
           acceptable for proof photos today.
           // ponytail: public blob URLs; ceiling = photos are link-shareable.
           // Upgrade path: access "private" + signed GET route when needed.
         · else → local disk: write to `${UPLOAD_DIR ?? ".uploads"}/${key}`,
           return url `/api/files/${key}`. Dev + self-host path ONLY — a
           Vercel function's filesystem is read-only outside /tmp, so a
           deploy with no BLOB_READ_WRITE_TOKEN and no S3 env must fail loud
           at startup of the first upload ("storage not configured"), never
           fall back to a disk that silently disappears between invocations.
    3. Local-disk serving route app/api/(global)/files/[...path]/route.ts:
       resolve against UPLOAD_DIR, `path.normalize` and REFUSE anything
       escaping the root (`..`), infer content type from extension, stream it.
       // ponytail: single-box local storage violates R4 statelessness on
       // multi-instance; the ECS exit is an S3 impl of putObject, one file.
    4. Upload validation helper in the same file:
         assertImageUpload(file: File): size ≤ 10MB, type startsWith
         "image/", extension in [png, jpg, jpeg, webp]. Throw typed errors
         ("file-too-large" | "not-an-image") — actions surface the code.
    5. VERIFY: node --test a storage.test.ts that round-trips a 1-byte png
       through the local impl and rejects an 11MB buffer and a .pdf.

A1b. STORAGE PORTABILITY — the Vercel Blob → S3 exit (decided 2026-07-22)
    Blob is the day-1 driver because it is zero-config on Vercel. The whole
    point of A1 is that leaving it later is a CONFIG change, not a refactor.
    Honest scope of that swap: one new file (~40 lines) + one env var. It is
    not literally one line — anyone who promises that is hiding the driver
    file — but ZERO business-logic files change. To keep it that way, four
    rules, all cheap, all enforced now:

    R1. ONE IMPORT SITE. `@vercel/blob` (and later `@aws-sdk/client-s3`) may
        be imported by storage drivers ONLY. Enforce mechanically, not by
        discipline: storage.test.ts greps the source tree and FAILS if
        "@vercel/blob" appears outside modules/core/storage*.ts. Same test
        catches the s3 client later for free. This is the rule that actually
        makes the swap safe; the other three are consequences.
    R2. DRIVER PICKED BY ENV, NOT BY IMPORT.
          STORAGE_DRIVER = "blob" | "s3" | "local"   (default: blob when
          BLOB_READ_WRITE_TOKEN is set, else local)
        The driver module is loaded with a dynamic import inside putObject so
        an unused SDK is never bundled. Adding S3 = create storage.s3.ts
        exporting the same putObject, add one case to the switch, set
        STORAGE_DRIVER=s3 + AWS_* / S3_BUCKET / S3_PUBLIC_BASE_URL in Vercel.
        That is the entire migration for new uploads.
    R3. STORE THE KEY, NOT ONLY THE URL. putObject already returns
        {url, pathname}. Persist BOTH wherever a file is recorded:
          · Order.proofImageUrl  = url        (what the UI renders)
          · Order.configs.proofKey = pathname (what a provider migration
            needs to rewrite the URL later)
          · label/zip artefacts: keep {url, key} inside Shipment.configs
        Without the key, moving providers means re-deriving paths from URL
        strings — the one thing that turns a config swap back into a project.
        No new column: configs is already Json? on both models.
        NEVER parse a stored URL for meaning, and never assume the host.
    R4. THE INTERFACE STAYS ONE FUNCTION. putObject is all doc 05 needs
        (proof photos, label zips). Do NOT pre-build getObject / deleteObject
        / signed URLs / multipart — S3 supports them, Blob supports them,
        neither is used, and speculative surface is the thing that makes a
        driver swap hard. Add a function to the interface the day a caller
        needs it, and add it to every driver in the same commit.
        // ponytail: public-URL-only storage. Ceiling = anyone with the link
        // can view a proof photo. Upgrade path (either driver): a
        // getSignedUrl(key, ttl) added to the interface + a /api/files auth
        // check; the DB already holds the key thanks to R3, so no backfill.
    ONE-TIME COST OF SWITCHING LATER (write it down so nobody is surprised):
    old Blob URLs keep resolving as long as the Blob store exists, so the
    swap needs no downtime; copying historic objects into S3 and rewriting
    the stored URLs is an optional cleanup script that reads configs.proofKey
    (R3) — an hour of work, not a migration project.
    VERIFY A1b: storage.test.ts contains the R1 grep assertion and passes with
    BLOB_READ_WRITE_TOKEN unset (local driver) — the same assertion the
    "self-host exit stays real" check at the end of this doc relies on.

A4. STATION SERVICE — modules/fulfillment/stations/service.ts
    New feature folder (stations/), because orders/service.ts is already the
    biggest file in the app and these functions share station-only helpers.
    Import the status map and orders queries through the domain barrel.
    Every function: explicit actor, orderScope() spread into every read,
    scope re-checked on every write (never authorise on a client id).

    recordScan(actor, input: {mode: "tracking"|"order"; value: string;
               confirmed?: boolean})
      → { group: TrackingGroup; requiresConfirmation?: {count: number} }
      1. Resolve the order set:
         · tracking mode: orders whose latest Shipment.trackingNumber matches
           value (≥22 chars: contains; shorter: case-insensitive contains —
           legacy prod repo:136-148), inside orderScope(actor).
         · order mode: value is a numeric order id → that order, then EXPAND
           to its group: all orders sharing its tracking number; if no
           shipment, all orders sharing its externalId prefix (externalId
           minus the final "-suffix" — legacy prod:2123-2130).
      2. THE CONFIRMATION GATE (legacy prod:2427-2456): if the set has >20
         rows and !confirmed → return {requiresConfirmation:{count}} and
         MUTATE NOTHING. The client re-calls with confirmed:true.
      3. Compute per-row wasScanned = status !== "ASSIGNED"  ← BEFORE step 4.
         (legacy is_scanned, prod:2268-2291 — not a column, computed.)
      4. Flip every ASSIGNED row → IN_PRODUCTION via the transition map, in
         one transaction; stamp assignedToId = actor.id where null (the
         "who worked this" slot, unwritten until now). This mutation IS the
         scan event — same rule as legacy `function=fulfillment`
         (prod:2268-2291).
      5. Return the group: {trackingNumber?, externalIdPrefix?, orders:[{id,
         externalId, status, wasScanned, quantity, filled, product, variant,
         sku, mockupThumb, designUrl, proofImageUrl, note, internalNote,
         basket: {name} | null, labelUrl?}], customer:{name}, isMultiUnit:
         any quantity>1}.

    fillOrder(actor, orderId, amount)
      → { order; basket?: {name} }
      1. Guard: order in scope, status IN_PRODUCTION, amount int ≥1 and
         ≤ (quantity - filled). No legacy "correction path" (it silently
         reduced counters on Filled/Completed rows, dev:1700-1706) — a
         mis-fill is fixed by an admin edit, audited.
      2. filled += amount. Do NOT change status when filled reaches quantity
         — "Filled" is derived (progress bar), the enum stays IN_PRODUCTION.
      3. BASKET ASSIGNMENT (port of legacy dev:1736-1766, race-proofed):
         if the order's tracking group has >1 rows AND none carries a
         basketPositionId:
           SELECT id FROM basket_positions WHERE status='AVAILABLE'
             ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED
         inside the same transaction; claim it (status OCCUPIED,
         trackingNumber = group's tracking) and set basketPositionId on ALL
         rows of the group. None available → error "no-available-basket"
         (the station shows it loudly; legacy threw the same).
      4. Return the refreshed group so the UI re-renders progress.

    attachProof(actor, input: {trackingNumber?|orderId?, file: File,
                overwrite?: boolean})
      1. Resolve group (same rules as recordScan). Guard scope +
         orders.status.update.
      2. OVERWRITE GATE: if any row is FULFILLED or SHIPPED and !overwrite →
         return {requiresOverwrite:true} (legacy OverWriteModal fired on
         'Pending Dropoff'|'Fulfilled', FulfillmentPage.jsx:122-139; ours
         keys on the enum).
      3. assertImageUpload → putObject key
         `proofs/<tracking|order>-<epoch>.png`.
      4. One transaction: every row gets proofImageUrl; every row NOT already
         past FULFILLED transitions to FULFILLED (fulfilledAt = now — the
         existing updateStatus semantics); basket freed: the group's
         BasketPosition → status AVAILABLE, trackingNumber null (keep
         basketPositionId on orders — it is history, legacy kept the display
         string too, dev:987-1002); audit ORDER_PROOF_UPLOADED once per
         group; notify nothing extra (FULFILLED is not a seller-notify
         status — matches the built updateStatus list).
      5. Return the group.

    completeHandoff(actor, input: {trackingNumber, confirmText: string})
      The legacy "type completed" ritual (FulfillmentPage2.jsx:268-315) —
      the point is a deliberate human check before the parcel leaves.
      1. confirmText.toLowerCase() !== "completed" → error "check-failed"
         (the UI shows "Test check failed", worker retypes).
      2. Group must exist, all rows FULFILLED (else "not-ready", listing
         offending ids).
      3. One transaction: every row → SHIPPED via updateStatus semantics
         (seller notification fires — the built code already notifies on
         SHIPPED); the group's Shipment rows get shippedAt = now; if a row
         has NO shipment yet, create one {trackingNumber, shippedAt} so
         SHIPPED never exists without a Shipment (audit SHIPMENT_CREATED);
         basket freed if still held.
      4. AFTER COMMIT: outbound seller webhook order_status (A6).
      5. Return {labelUrl} (latest shipment's) so the station can open/print.

    linkLabel(actor, input: {orderIds: number[], trackingNumber: string,
              labelUrl: string (https), provider?: string, method?: string,
              cost?: string})
      Guard orders.labels.manage. For each order in scope: create a Shipment
      {trackingNumber, labelUrl, provider, method, cost} (one per order —
      the schema is one shipment row per order; a group shares the tracking
      number, not the row). Audit SHIPMENT_CREATED per order. AFTER COMMIT:
      shipping_added webhook to each distinct seller (A6). This is the
      manual path that replaces legacy "PUT /orders/:id with label_url"
      (prod:2677-2696) — in the new schema tracking/label NEVER sit on
      Order, only on Shipment.

    quickUpdate(actor, input: {keyword, to: FulfillmentStatus, note?})
      → {updated: n, skipped: [{id, reason}], rows}
      Port of PATCH update-by-keyword, prod behaviour NOT dev: match by
      tracking number only (contains, truncate-22) — dev matched 15 ILIKE
      fields including note text and once updated whatever it hit with ZERO
      validation (dev:906-918). Ours: rows in scope, canTransition applied
      per row; legal ones updated (through the same updateStatus core so
      notifications/resumeTo hold), illegal ones reported skipped with the
      transition error code. This function is the entire quick-scan backend.

    schema.ts: zod for every input above (scanSchema value: min 10, max 40,
    truncated server-side to last 22 for tracking mode — mirror what the UI
    does so a raw API caller gets identical behaviour; legacy FE truncated at
    22, FulfillmentPage.jsx:19,71-73; min-length note: legacy had 11 on one
    station and 10 on another — standardise on 10).
    actions.ts: one "use server" wrapper per function, each: guard →
    withValidation(schema) → service → revalidatePath("/fulfillment") (and
    "/orders" where rows changed).

    not: tracking is its own axis (the status dictionary at the top says so),
    so an order sits at SHIPPED forever while its shipment reads "delivered".
    Nothing else ever sets DELIVERED, which means the status exists and is
    unreachable in practice.
    Not decided in code on purpose — it is a business rule about when an order
    is finished, and the carrier is only one opinion about that. Cheapest
    version if the answer is yes: applyTrackingUpdate calls applyStatusChange
    for rows still at SHIPPED, which already notifies the seller.

O2. WHO PAYS FOR A LABEL?  purchaseLabels writes the cost onto the Shipment and
    charges nobody. Doc 04's money path bills sellers at ASSIGNMENT for the
    product; shipping is currently absorbed. If labels should be billed, that
    is a ledger move and belongs with the own-shipping price question already
    parked in doc 04 (D1), not bolted on here.

O3. AUTO-PURCHASE ON IMPORT.  Deliberately not ported (legacy bought on every
    create path). Revisit only once the grouping and skip rules have been
    trusted on real orders for a while — the ponytail comment in purchase.ts
    names it as the upgrade path.
