0b. DICTIONARIES (memorise; they resolve every mapping question)
--------------------------------------------------------------------------------
COUNTER SEMANTICS (one convention, the material one — standard warehouse
math; matches the tooltip translations shipped to the floor):
  onHand    = units physically present, INCLUDING reserved   (col: quantity)
  reserved  = held for assigned orders, still on the shelf
  needed    = shortage backlog recorded when a reservation failed
  bad       = damaged/unusable units                      (col: badQuantity)
  AVAILABLE = max(onHand − reserved − needed, 0)   ← COMPUTED, NEVER STORED
  (WarehouseInventory.stock exists from the legacy-A migration; it is NOT
  maintained by new code. Leave the column, stop reading it, note in selects.)

MOVEMENT TYPES — new enum InventoryMovementType vs both legacy ledgers:
  NEW               MATERIAL ledger wrote        PHYSICAL ledger wrote
  RECEIPT           receipt                      receipt
  MANUAL_IMPORT     —                            manual_import
  MANUAL_ADJUSTMENT manual_adjustment            manual_adjustment
  RESERVE           material_reserve             reserve
  RESERVE_RELEASE   material_reserve_release     reserve_release
  CONSUME           material_consume (qty<0)     assign (qty<0)
  RETURN            material_return              return
  NEEDED            material_needed              needed
  NEEDED_RESOLVED   material_needed_resolved     needed_resolved
  Sign convention (kept from legacy): movements that take stock away
  (CONSUME) carry NEGATIVE quantity; the ledger renders red/green off sign.

RECEIPT STATUSES — enum ReceiptStatus: PENDING, PARTIAL, COMPLETE, REJECTED
  (material system's set; physical's unused `approved` is dropped).
SHIPMENT STATUSES — enum ReceiptShipmentStatus: PENDING, PARTIAL_RECEIVED,
  RECEIVED, REJECTED (material's set; physical lacked PARTIAL_RECEIVED —
  we unify on the richer per-line delta-receive semantics for both).
RESERVATION STATUSES — enum ReservationStatus: RESERVED, CONSUMED, RELEASED,
  RETURNED (exactly the four values legacy ever wrote).
BOM STATUSES — enum BomStatus: DRAFT, ACTIVE, INACTIVE.
BOM STAGES — enum BomStage: PRODUCTION, PACKING, SHIPPING, OTHER (legacy
  exact list, ProductVariantBomModal.jsx:22).
MATERIAL TYPES — enum MaterialType: RAW_MATERIAL, PACKAGING, SEMI_FINISHED,
  CONSUMABLE, OTHER (legacy exact list, MaterialItemsPage.jsx:23-29).
  UOM stays a FREE-TEXT string, default "pcs" — legacy never constrained it
  and the floor types real units ("m", "roll", "kg"); do not invent an enum.

NAME COLLISION WARNING for the cutover: legacy table `Materials` is NOT
materials — it is an attribute catalog (leather/canvas/wood) for the
never-rebuilt SKU/addon system. Raw materials live in legacy `MaterialItems`.
Phase E maps MaterialItems → our `materials`; legacy `Materials` is NOT
migrated (its dependents — OrderAttribute, ProductAddonRule, techniques,
positions — were commented out of the legacy menu and are not rebuilt).

A3. DECISIONS TAKEN DURING THE A1 BUILD — RECORDED, DO NOT RE-LITIGATE
    A1 above specifies columns, not referential policy. Three questions came
    up while writing the models; each is answered once, here, because the
    answer generalises to every history table this system will ever grow.

    1. THE LEDGER'S REFERENCE IDS CARRY NO FOREIGN KEYS.
       InventoryMovement.{reservationId, bomId, bomLineId, orderId} are plain
       Int? columns. Deliberate, not an omission:
         · updateBom does a FULL LINE REPLACE (D1 — deleteMany + createMany).
           An FK to bom_lines makes that either impossible (RESTRICT blocks
           the edit) or destructive (CASCADE silently deletes the history of
           what an order actually consumed). Both outcomes are worse than a
           dangling id.
         · A movement is a statement about the PAST. Nothing that happens
           later — a BOM edit, an order purge, a reservation cleanup — may
           block it, rewrite it, or take it with them. That is what
           "append-only" has to mean to be worth anything, and it is also
           what makes the reconcile-from-movements upgrade path (§DELIBERATELY
           NOT PORTED) possible at all.
       The cost is that a join may find nothing. That is correct: the ledger
       renders "bom 41" as a plain reference when the BOM is gone, and the
       row still tells you the quantity, the item and the date, which is the
       part that matters. Generalises to: history/audit rows keep ids, never
       foreign keys.

    2. InventoryReservation.orderId IS A REAL FOREIGN KEY (and required).
       The opposite call to (1), for the opposite reason: a reservation is
       not a record of the past, it is a LIVE CLAIM on stock. An orphaned
       reservation holds `reserved` units forever, and nothing self-heals it
       — availableOf subtracts it on every page, every preview and every
       future assignment, so the shelf silently shrinks. Integrity here is
       worth the constraint. Item and warehouse are real FKs on both models
       for the same reason plus the joins the pages need.
       Rule of thumb: FK when the row makes a claim on something live; plain
       id when the row states something that already happened.

    3. USER LINKS ONLY WHERE A PAGE NAMES THE PERSON.
       Relations added: InventoryMovement.createdBy (the Movements table has
       a User column, B2), StockReceipt.createdBy/approvedBy (the receipt
       detail shows both). Left as plain String columns: Bom.createdById/
       updatedById, InventoryReservation.createdById — no screen in this doc
       displays them, and AuditLog already holds the who-did-what trail with
       actor, before/after and reason. Adding a relation "just in case" costs
       a back-relation on User, which is a real edit to the most-referenced
       model in the schema, for a join nobody performs.
       If a later screen needs one of those names, adding the relation is a
       pure-metadata migration (the column and its values already exist).

B5. WHAT PHASE B ACTUALLY DID DIFFERENTLY (built 2026-07-22 — read before
    phases C/D, both of which call into this code)

    1. resolveNeeded settles PARTIALLY, and against UNRESERVED units.
       B2 above says "if needed > 0 and available now covers it". Built as
       settled = min(needed, unreservedOf(row)), which differs twice:
         · Partially. Three units arriving against a backlog of five clears
           three. Waiting for full coverage leaves a shortage that real stock
           already covers, and `needed` only ever suppresses availability —
           so under-resolving makes the shelf read emptier than it is.
         · Against UNRESERVED units (quantity − reserved), not availableOf.
           availableOf subtracts `needed` itself, so using it here would
           subtract the backlog from the very number deciding how much of the
           backlog to clear — three units would settle one, then the next
           call one more. Settling against units already promised to another
           order would be worse still: one order's stock paying off another
           order's shortage.
       This is why counters.ts exports TWO named functions. Neither is bare
       arithmetic anywhere else; the doc's grep check covers both.

    2. Receipts is not in the /inventory tab strip yet. It arrives with its
       route in phase C. A tab that lands on the coming-soon catch-all is
       worse than a tab that isn't there.

    Also worth knowing:
    · B3's site-scope test asserts through the SERVICE, not the action. The
      scope guard lives in assertSite(); the action adds only
      requirePermission, which needs a session the node --test harness has no
      way to mint. Same choice the stations suite already made.
    · B4's nav + i18n (build-order step 10) was done HERE rather than saved
      for a sweep: every string went through t() as it was written, so there
      was nothing left to sweep. ~150 keys × 7 locales are in place;
      phases C/D extend the same `inventory` namespace.
    · t() takes a key and nothing else — there is no interpolation in this
      i18n. Counts and names compose in JSX (see delete-material-dialog).
      Do not write t("…", { count }); it silently renders the raw key.
    · Material status labels reuse `catalog.statuses.*` — the same four

PHASE C — RECEIPTS  (modules/inventory/receipts/)  [needs doc 05 A1 storage]
--------------------------------------------------------------------------------
The workflow, exactly as legacy ran it (the parts users saw), minus its dead
endpoints: an ADMIN creates a receipt (one warehouse; 1..n shipments; each
shipment 1..n lines); the WAREHOUSE receives per shipment, entering received
+ rejected per line, possibly across several sessions (partial); evidence
photos attach per shipment; a report powers the ETA/variance tiles.
Receipt-level approve/reject/edit service methods existed in legacy but the
UI never called approve; we port ONLY what was used: create · edit-while-
pending (admin) · per-shipment receive · reject · evidence · report.

C1. service.ts
    createReceipt(actor, input)   guard inventory.receipts.create.
      Input mirrors the legacy modal: {itemType, warehouseId, provider?,
      note?, shipments: [{vendorId?, shipmentCode? (default "S"+n),
      trackingNumber?, carrier?, expectedArrivalAt?, lines: [{materialId|
      productVariantId, requestedQuantity ≥1, unitPrice?, note?}]}]}.
      Code = "SR-" + yyyymmdd + "-" + 5 random upper alnum (legacy format,
      one series). Validate warehouse/vendor/item existence up front.
    updateReceipt(actor, id, input)  admin, PENDING only; wipe-and-recreate
      shipments+lines (legacy repository semantics — simplest correct thing
      while nothing is received yet).
    receiveShipment(actor, receiptId, shipmentId,
                    lines: [{lineId, receivedQuantity, rejectedQuantity?}])
      guard inventory.receipts.receive + warehouseScope (admin any site).
      THE CORE RULES (all legacy-verified, material-stock-receipt.service.ts
      :555-694):
      · allowed only while shipment ∈ {PENDING, PARTIAL_RECEIVED} and
        receipt ∈ {PENDING, PARTIAL}
      · caller supplies received for EVERY line of the shipment
      · per line, inside ONE $transaction with SELECT … FOR UPDATE on the
        line row: newReceived ≥ currentReceived (MONOTONIC — a re-receive
        can only grow); stockDelta = newReceived − currentReceived;
        stock row onHand += stockDelta; movement RECEIPT with the delta
        {referenceType:"stock_receipt_shipment", referenceId}; then
        resolveNeeded(). Delta-only math is what makes partial receiving
        re-approvable without double-counting — THE invariant of this phase.
      · recompute shipment status: RECEIVED when every line
        received+rejected ≥ requested; else PARTIAL_RECEIVED. Roll up
        receipt: all shipments RECEIVED → COMPLETE (+approvedBy/At);
        any progress → PARTIAL.
    rejectReceipt(actor, id, reason?)   any non-COMPLETE receipt: status
      REJECTED, rejectReason, pending/partial shipments → REJECTED. NO stock
      effect (legacy rule — rejected goods never entered stock).
    addEvidence(actor, receiptId, shipmentId, files[])   ≤10 files/call;
      assertImageUpload each (doc 05 A1); putObject key
      `receipts/receipt-{id}-shipment-{sid}-{ts}-{i}.{ext}`; append
      {url, filename, originalFilename, mimeType, size, uploadedAt,
      uploadedById} into shipment.evidence Json. Guard = receive roles.
    shipmentsReport(actor, {upcomingDays = 14 ≤ 90, warehouseId?})
      → {upcomingEta, overdueEta, partialReceipts, quantityVariances}
      where variance = received + rejected − requested per line, non-zero
      listed (computed, never stored — legacy rule).
    audits: RECEIPT_CREATED / RECEIPT_RECEIVED (per receive call, with the
      deltas) / RECEIPT_REJECTED.

    Tiles from shipmentsReport: Upcoming ETA (14d) · Overdue ETA (red>0) ·

PHASE D — BOM  (modules/inventory/boms/)

D1. service.ts — configuration side:
    listBoms / getBom — every list row carries summary {lineCount,
      mappedLineCount, requiredLineCount, unmappedLineCount} (the
      "Incomplete lines" concept = lines with materialId null).
    createBom(actor, productVariantId, input) / updateBom(actor, id, input)
      guard boms.manage. Input: {name (default "<variant name> BOM"),
      version? (server assigns next when blank), status, note?, lines:
      [{materialId? , componentSku, componentName?, quantityPerUnit > 0,
      unit, wastageRate (UI sends percent/100), stage, required, sortOrder,
      note?}]}. Update = full line replace (deleteMany + createMany —
      legacy semantics, simplest correct). RULE: exactly ONE ACTIVE Bom per
      variant — activating (create-as-active, update-to-active, activate())
      deactivates siblings in the same transaction (bom.service.ts:390-489).
    activateBom(actor, id)   REFUSES a BOM with zero lines (legacy :476-478).
    duplicateBom(actor, id)  next version, DRAFT.
    deleteBom(actor, id)     soft: INACTIVE + deletedAt.
    previewConsumption(actor, {bomId? | productVariantId? | lines?,
      quantity, warehouseId?})  → per line requiredQuantity = qty ×
      quantityPerUnit × (1 + wastageRate), joined to availableOf per
      warehouse, shortage = max(required − available, 0), mappingStatus.
    audits: BOM_CREATED/UPDATED/ACTIVATED/DELETED.

D2. service.ts — the ORDER-FLOW LIFECYCLE (the reason BOMs exist).
    Three functions, called from the fulfillment domain through
    inventory/index.ts. ALL are no-ops unless env INVENTORY_ORDER_FLOW=1 —
    port of legacy's ORDER_INVENTORY_ENABLED master switch
    (order.service.ts:6412-6422): stock enforcement stays OFF until the
    counts are trusted post-cutover, and flipping it needs no deploy.
    Warehouse for all three = Order.warehouseId (← the fix; legacy used the
    scanning user's home warehouse).

    reserveForOrder(tx, order)       call site: assignOrders (doc 04 B2),
                                     inside its existing transaction
      1. Variant has an ACTIVE Bom → explode required lines: per material
         quantity = ceil(orderQty × quantityPerUnit × (1 + wastageRate)),
         aggregated per material. Any required line unmapped → error
         "bom-line-unmapped" (refuse, legacy :1068-1071).
         No active Bom → single line: the order's productVariantId itself
         (the finished-goods path), quantity = orderQty.
      2. Idempotent: an existing RESERVED/CONSUMED reservation for
         (orderId) is a no-op success.
      3. Shortage path: if any item's availableOf < required → write NEEDED
         movement + needed += shortage (once per order per item) and FAIL
         the assignment with "insufficient-stock" listing the items —
         matches legacy, which threw and blocked assignment (:836-844).
      4. Success path: first resolveNeeded for any prior shortage rows of
         this order, then per item an ATOMIC GUARDED update —
           UPDATE … SET reserved = reserved + q
           WHERE warehouse_id=… AND …item… AND
                 (quantity − reserved − needed) >= q
         (raw SQL like legacy :786-793; rowcount 0 → concurrent race →
         fail "insufficient-stock") — then a Reservation row + RESERVE
         movement per item.
      NOTE the counter convention: reserve does NOT touch onHand (§0b).
    consumeForOrder(tx, order)       call site: doc 05's recordScan flip
                                     ASSIGNED→IN_PRODUCTION (and any other
                                     path entering IN_PRODUCTION)
      Idempotent via existing CONSUME movement for the order. Per
      reservation: q = quantity − consumedQuantity; guarded
      onHand −= q AND reserved −= q (both must stay ≥0); reservation →
      {consumedQuantity = quantity, status CONSUMED}; movement CONSUME with
      NEGATIVE quantity.
    releaseForOrder(tx, order)       call site: updateStatus → CANCELLED
      CONSUMED → add back (onHand += q), status RETURNED, movement RETURN.
      RESERVED → reserved −= q, status RELEASED, movement RESERVE_RELEASE.
      Idempotent; orders past SHIPPED never release (terminal guard already
      in the status map).

D5. WHAT PHASE D ACTUALLY DID DIFFERENTLY (built 2026-07-22)

    1. THE LIFECYCLE HOOKS LIVE IN applyStatusChange, NOT AT THE CALL SITES
       D2 names recordScan (ASSIGNED→IN_PRODUCTION) and updateStatus→CANCELLED.
       Both funnel through orders/service/status-change.ts, and so does every
       other path that moves an order — the row menu, quick scan, the handoff,
       the public API. Hooking the two named callers would have left the others
       silently building orders out of stock nobody took. One hook in the
       shared function covers "any other path entering IN_PRODUCTION" the way
       D2 asks for, and cannot be forgotten by a future caller.
       reserveForOrder stays in assignOrders, which is correct: it is the only
       thing that assigns, and the reservation must share the money's
       transaction.

    2. THE SHORTAGE BACKLOG IS WRITTEN AFTER THE FAILURE, NOT DURING IT
       D2 step 3 says to write NEEDED and fail. Both cannot happen in one
       transaction — the failure rolls the write back. So reserveForOrder
       THROWS with the item refs attached, and assign's catch calls
       recordShortage() on a fresh transaction. Same outcome the doc wants
       (shortage visible, assignment refused), and it actually persists.
       recordShortage is idempotent per order per item, so a retried
       assignment does not stack the same shortage twice.

    3. THE FUNCTIONS TAKE AN ORDER ID, NOT A SHAPED ORDER
       StatusSubject carries only what the status machine needs; widening it
       would have forced every caller to select warehouseId/productVariantId
       for a feature that is off. The hooks load the order themselves inside
       the caller's transaction, and cost nothing when the flag is unset.

    4. Preview surfaces an unmapped REQUIRED component as a LINE with
       mappingStatus UNMAPPED plus `blocked: true`, rather than throwing. The
       preview panel is exactly where someone should discover it.

    5. /admin/boms Configs and Coverage share ONE route via ?tab=, not two
       navbar tabs. The Administration row already carries eight sections;
       "BOMs" and "Coverage" sitting there as peers of Users and Warehouses
       would say they are unrelated, which is the opposite of true.

    Not built, deliberately: an "activate" confirmation, BOM import/export, and
    per-stage previews. None is in the doc; ask before adding.

E4. WHAT PHASE E ACTUALLY DID DIFFERENTLY (built 2026-07-22)

    0. THE TABLE NAMES ARE NOT WHAT THIS DOC ASSUMED — READ BEFORE EDITING.
       Checked against origin/prod:prisma/schema.prisma (tip 10117f7). Legacy
       is INCONSISTENT and the script matches it exactly:
         · every MATERIAL table is PLURAL via @@map — "MaterialItems",
           "MaterialInventories", "MaterialStockReceipts", "Boms", "Vendors" …
         · the four PHYSICAL tables have NO @@map, so Prisma named them after
           the model and they are SINGULAR — "PhysicalStockReceipt",
           "PhysicalStockReceiptShipment", "PhysicalStockReceiptLine",
           "InventoryMovement". "PhysicalInventories" IS plural.
         · column names differ the same way: PhysicalInventories keys on
           `variant_sku`; PhysicalStockReceiptLine and InventoryMovement use
           `physical_variant_sku`.
       Get one wrong and the cutover aborts on table-not-found. The fixture
       encodes all of it, which is what proves the script spelled them right.

    1. migration_report IS A REAL TABLE, not the TEMP table §E1 specifies.
       A temp table dies with the psql session — exactly when someone wants to
       read the orphan list. Dropped alongside the legacy tables afterwards.

    2. SYSTEM B OVERWRITES SYSTEM A on shared shelves. warehouse_inventory
       already holds rows from the main cutover (system A, deleted from legacy
       prod 2026-06-18). PhysicalInventories is the live finished-goods data,
       so the upsert is DO UPDATE, not DO NOTHING — otherwise the cutover
       preserves counts that stopped being maintained ten months ago.
       Mutation-tested.

    3. UNKNOWN MOVEMENT TYPES ARE SKIPPED, NOT COERCED. §E2 asks for "report,
       not crash"; the third option — bucket it as MANUAL_ADJUSTMENT — is
       worse than both, because the ledger is what a wrong count gets explained
       with and a mislabelled row explains nothing. Reported with its legacy id
       and type, and skipped. Mutation-tested.

    4. THE ONE-ACTIVE-BOM RULE IS ENFORCED DURING MIGRATION. §E1.8 does not
       mention it, but our services assume exactly one ACTIVE BOM per variant
       and legacy had no such constraint — two would leave reserveForOrder
       picking arbitrarily. Newest version wins, the rest go INACTIVE, and the
       variant is reported. Mutation-tested.

    5. RECEIPT IDS ARE RE-ISSUED, CODES ARE KEPT. Both legacy series start at
       id 1 and would collide in one table. MSR-/PSR- codes stay unique
       alongside the new SR- series, which is what lets the floor find an old
       receipt by its paperwork. Temp id maps carry shipments and lines to the
       right parent — the place a cutover most easily attaches a parcel to
       somebody else's receipt, so the assertions check it explicitly.

    6. Legacy `Materials` (the leather/canvas/wood attribute catalog) is in
       the fixture PURELY so an assertion can prove none of it leaked into
       `materials`. §0b warns about the collision; this makes the warning
       executable.
