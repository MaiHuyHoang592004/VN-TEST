0c. CUTOVER NOTES FROM THE BUILD  (written 2026-07-22, as A-F shipped)
--------------------------------------------------------------------------------
Everything below was discovered while BUILDING A-F. None of it blocks the
build; all of it has to be decided or done AROUND the legacy cutover
(finished/02 + doc 06 E). Each item says who it hurts if it is skipped.

C1. LEGACY REFUNDS ARE INVISIBLE TO THE NEW DOUBLE-REFUND GUARD.  ★ money ★
    Phase B decides "has this order already been refunded?" by reading the
    LEDGER: a COMPLETED REFUND transaction whose metadata.orderIds contains
    the id (orders/service/refund.ts). Rows imported from legacy have no
    such metadata, so an order refunded in the OLD system can be refunded
    again in the new one — real money, paid twice, with nothing to flag it.
    DO ONE OF (before the first refund runs post-cutover):
      (a) backfill metadata = {"orderIds":[…]} on imported REFUND rows from
          whatever the legacy refund recorded (its description carries the
          order ids in most rows), or
      (b) rely on the second guard — a refunded order is CANCELLED, and
          cancelled orders are skipped — which holds ONLY if the cutover
          brings legacy "Refund" status across as CANCELLED. Verify that in
          migrate-legacy.sql before trusting it.
    Cheapest safe answer: do (b) deliberately, assert it with a row count
    ("no legacy-refunded order arrives in a non-CANCELLED status"), and note
    (a) as the fallback if the assertion fails.

C2. PRICE UNITS DECIDE WHETHER "RECALCULATE" IS SAFE.  ★ money ★
    Phase E2 re-prices unpaid orders from today's price list. If legacy
    prices came across in the wrong unit (the dollars-vs-cents question
    still open in finished/02), every recalculated order is wrong by 100x.
    Do not expose the Recalculate button to staff until the unit question is
    closed and spot-checked. It refuses PAID orders already, so the blast
    radius is unassigned orders only.

C3. TICKET HISTORY ARRIVES WITHOUT ITS CONVERSATION.
    Legacy tickets have no replies table (Phase A added one). Imported
    tickets will render as an opening post and an empty thread, which is
    accurate — the conversation happened in chat — but support should be
    told, or they will read it as data loss. Ticket ATTACHMENTS live in the
    legacy S3 bucket: they are part of the G4 file-asset decision.

C4. ORDER ARTWORK URLs POINT AT THE DYING SERVER.
    Order.imageUrl and Mockup.url on imported rows are Google Drive links
    and legacy uploaded/ paths. Phase E3 lets staff replace either by hand,
    one order at a time — fine for a handful, not for a backlog. If those
    images matter after the cutover, they are a bulk copy job (G4), not a
    UI task.

C5. NOTHING MIGRATES VENDORS' EXPENSE HISTORY.
    Phase C's expense_categories / expense_entries are NEW tables. The
    legacy expense module's rows are not in migrate-legacy.sql and nobody
    has asked for them. DECIDE: import them (a small script — category
    names + entries), or start the books fresh at cutover and keep the old
    system's read-only export as the archive. Vendors themselves DO come
    across (doc 06).

C6. THE WEBHOOK SIGNATURE CHANGE IS THE ONE BREAKING CHANGE FOR SELLERS.
    x-api-key → X-Signature (doc 05 A6). It is already on the F4 migration
    map inside the dashboard; G3 is what makes sure a human also sends it.
    API KEYS themselves keep working (imported as hashes) — test one real
    key against /api/v1 before announcing anything, as G3 says.

C7. SEARCH IS UNINDEXED SUBSTRING MATCHING, AND THAT IS A SCALE CEILING.
    Phase D2 matches with ILIKE '%term%', which no btree index can serve, so
    every ⌘K keystroke is a sequential scan of orders, product_variants and
    users. Guarded today by: signed-in only, per-group cap of 5, a minimum
    query length of 2, and a per-user rate limit (RATE_LIMITS.search).
    Fine at today's volume; at roughly 100k orders it becomes noticeable and
    at 1M it saturates the database. UPGRADE PATH, when the numbers say so:
    a pg_trgm extension + GIN indexes on orders.external_id,
    shipments.tracking_number, product_variants.sku and users.email/name —
    one migration, no application code changes. Measure before doing it.

C8. THE CLIENT-SIDE SEARCH INDEX IS GONE ON PURPOSE.
    /api/search/all used to ship the whole index to the browser for fuzzy
    matching. With real rows that is a bulk export of everything the caller
    may see, and a PARTIAL index silently hides rows, so both were removed
    (doc 07 D2). The user-visible loss is typo tolerance. If sellers ask for
    it back, it comes from pg_trgm similarity() in C7, not from the client.

PHASE B — SELLER MONEY SELF-SERVICE  (modules/finance/requests/)
--------------------------------------------------------------------------------
Legacy sellers could REQUEST money moves (billing.controller.ts): a top-up
request and a refund request, both creating PENDING transactions an admin
then approves — and doc 04 C1's approve/reject flow is ALREADY BUILT. This
phase adds the request side + evidence, and the admin bulk-refund action.

B1. requestTopUp(actor, {amount > 0, method, note?, files?})
      guard transactions.read.own (any seller). Creates Transaction
      {type TOPUP, status PENDING, amount, paymentMethod, note} + evidence
      files → storage key transactions/<publicId>/… → NEW COLUMN
      Transaction.evidence Json? (migration transaction_evidence — this is
      the doc 04 C2 deferral, now unblocked by doc 05 A1). Notifies every
      transactions.approve holder (NotificationType TRANSACTION_REQUESTED —
      add to enum + META + 7 locales). NO balance change until approval —
      the built settlePendingTransaction handles that atomically.
B2. requestRefund(actor, {orderIds, reason REQUIRED, amount?, files?})
      guard transactions.read.own + every order inside own scope. Ports the
      legacy guards exactly (transaction.service.ts:148-345): orders must
      not be CANCELLED/already-refunded · no second PENDING refund request
      touching the same order (check pending REFUND transactions' metadata)
      · amount defaults to Σ(baseCost + shipping cost) of the orders and is
      CAPPED there. Creates PENDING REFUND transaction with
      {metadata: {orderIds, reason}} + evidence + notify approvers.
B3. adminRefundOrders(actor, {orderIds, idempotencyKey})
      guard orders.refund (the permission reserved since phase 2 — grant
      stays ADMIN). The legacy bulk refund, rebuilt on our ledger: group by
      seller; refund = Σ(baseCost + shipment costs), full only (legacy had
      no partial); skip orders already refunded (movement/transaction
      check); ONE applyBalanceMove(REFUND) per seller (core/ledger — never
      a second credit routine) + orders → CANCELLED via updateStatus (the
      dictionary: legacy "Refund" status = money action + terminal state)
      with note "refunded" + audit + the seller notification the ledger
      flow already sends. UI: the orders-page row/bulk action ("Refund…"
      dialog: order list w/ per-order cost, total, confirm).
B4. UI: /profile/billing gains "Request top-up" and "Request refund"
      buttons + dialogs (evidence dropzone, running total for refunds);
      /admin/transactions rows show evidence thumbnails (the C2 deferral)
      and REQUESTED rows surface in the approvers' bell.
B5. TESTS: refund request over the cap rejects · duplicate pending request
      on the same order rejects · admin refund is idempotent under the key
      and skips already-refunded · approve of a requested top-up moves
      balance exactly once (extends the doc 04 C1 concurrency lesson).
